## Upgrade notes

Moves every Unique image and the release-locked Conduct charts (`sbx-gateway`, `sbx-templates`)
from `2026.37.0` to `2026.40.4`. The generic `backend-service` (10.5.1), `web-app` (5.3.0) and
`ai-service` (3.0.0) charts are unchanged.

**No new required instance values.** Every setting the services gained in this window is optional
or defaulted; no key this repository sets was renamed or dropped.

New release defaults in `06-applications/defaults/`, adopted with the tag:

| Service | Key | Value | Effect |
|---|---|---|---|
| all web apps | `FEATURE_FLAG_ENABLE_TOAST_V2_UN_23011` | `"true"` | New notification toasts. Set in `defaults/web-apps/_all.yaml`, so every web app including `theme` receives it; frontend-only and inert where the app does not read it |
| chat backend | `SOURCE_AVAILABLE_TOOLS_REMOTELY` | `"true"` | Chat fetches its tool list from assistants-core; falls back to the built-in list if unreachable |
| configuration backend | `CHAT_BACKEND_API_URL` | `http://backend-service-chat.unique.svc` | Lets the configuration service read company settings stored in the chat backend; unset only skips that source |

These three are optional upstream; this repository adopts them so the fleet runs one
configuration. Two consequences to weigh before syncing:

- **`defaults/` is shared across environments.** An environment still pinned to an older release
  inherits these the moment the `deploy` branch advances. The toast flag is inert where unread,
  but `SOURCE_AVAILABLE_TOOLS_REMOTELY` changes where chat sources its tool list — if a held-back
  environment's assistants-core does not serve that endpoint, confirm the documented fallback
  before advancing `deploy` there.
- **`CHAT_BACKEND_API_URL` adds a reverse edge.** Chat already reads its feature-flag config from
  configuration-backend at startup; configuration-backend now reads company settings from chat.
  Confirm that read is lazy or retried before relying on a simultaneous cold start of both —
  configuration-backend runs at `replicaCount: 1`, and every backend service exits 1 without it.

**Conduct `sbx-gateway` PDB:** the overlay's `pdb.minAvailable: null` was added for 2026.37.0,
which flipped that default to `1` and blocked node drains. It has been carried forward to
2026.40.4 without re-checking the chart. If the default was reverted the override is harmless
dead weight; if the key was renamed or restructured the override suppresses nothing and
`maxUnavailable: 1` may be rejected alongside a resurrected `minAvailable` — and because the app
sets `skipSchemaValidation: true`, that surfaces at reconcile rather than render. Re-check it.

**Conduct `sbx-templates`:** the SandboxTemplate chart advances three release-weeks while
`agent-sandbox-controller` stays on its pinned digest, and that controller owns the CRD the
template validates against. A field the pinned CRD does not know is pruned silently rather than
rejected — the 0.4.5 behaviour the controller's own app spec warns about. Re-pin the controller,
or confirm 2026.40.4 leaves the SandboxTemplate schema unchanged, before enabling sandboxes.

**Conduct `sbx-gateway`:** the chart dropped its string-form `allow*Config` /
`stripRequestQueryParamsConfig` values in favour of the list forms. This repository sets
**neither** form and inherits the chart's defaults, so it needs no change — but a fork that set
the string forms will find them silently inert, and `skipSchemaValidation: true` on the app spec
means nothing flags that at render time. Compare your overrides against the new chart defaults.
